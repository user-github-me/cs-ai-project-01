A system that senses and acts
Combine the parts
An integrated smart system connects physical hardware, communication and software to carry out
a useful task. Sensors collect information; processing interprets it and selects an output; actuators
change the world. A network lets components exchange data or use remote services. Some
systems use fixed rules, some use learned models, and some combine both.
Follow one complete workflow
Sense
Communicate
Decide
Act
The changed environment supplies the next observation. The communication step may be local, remote or
partly unnecessary for a self-contained controller.
Use the body analogy carefully
Sensors resemble senses, actuators resemble muscles and communication links resemble nerves.
Software coordinates the response. This is an analogy for the roles, not a claim that the machine
has a human mind. Explain the actual mechanism: what is measured, what message is sent, what
computation runs and what physical output follows.

Example: an irrigation system
Trace the flow of information
Stage
Illustrative design
Measure
Soil-moisture sensors report readings and timestamps.
Communicate
A low-power network sends readings to a local gateway.
Decide
A controller selects a watering action using targets and
constraints.
Act
A driver energises a valve; later readings show the effect.
Add learning only when it has a role
A fixed threshold can open a valve when soil is dry. A learned policy might instead use moisture,
recent rain and other state variables to trade off water use and crop needs. Reinforcement
learning would require a defined reward and a process for updating the policy from experience.
Merely connecting a sensor to Wi-Fi does not make the system learn.
Check assumptions before action
Sensors can drift; messages can arrive late; a valve can fail. Timestamp readings, detect
implausible values and monitor the effect of each action. A real deployment needs
domain-specific limits and testing. This example explains an architecture rather than prescribing
watering durations for a particular crop.

Real-time means meeting a deadline
Correctness includes timing
A real-time system must produce the required response within a specified deadline. “Real-time”
does not simply mean very fast. Missing a hard deadline can make a system fail its requirements;
missing a soft deadline reduces service quality. Batch work, such as a monthly report, usually has
different timing needs.
Illustrative delay distance at 30 m/s
Delay before response
Distance travelled
500 ms = 0.500 s
30 × 0.500 = 15 metres
50 ms = 0.050 s
30 × 0.050 = 1.5 metres
5 ms = 0.005 s
30 × 0.005 = 0.15 metres
Interpret the calculation correctly
Distance during delay = speed × delay. This is only the distance travelled before a response
begins, not total stopping distance. Sensing, processing, communication, actuation and physical
braking all contribute to a real system. Moving a critical computation locally removes some
communication delay, but it does not guarantee a particular safe outcome.

Networking for a behaviour-based
agent
Separate the fast loop from shared services
A useful architecture keeps time-critical sensing, policy evaluation and actuator control near the
device. A network can carry telemetry, coordinate multiple devices or distribute reviewed model
updates. Training may occur centrally while a fixed policy runs locally. A system can continue its
local task during a link outage only if it was designed to do so.
Two connected responsibilities
Device: observe / act
Network: data + updates
Server: analyse / train
Local action does not have to wait for every cloud exchange. This is an architectural choice, not a property of
all AI systems.
Make messages interpretable
Include a device identity, timestamp, sequence number, units and model or policy version where
needed. Reject stale or unauthorised commands. Delayed feedback must be associated with the
action that produced it before a learning update is made. Network loss can reduce the evidence
available for training; it should not silently become a reward of zero.

Automation changes work and errors
A spectrum of responsibility
Mode
Who does what?
Manual
A human performs the task directly.
Assistance
The system supports selected actions or provides alerts.
Partial automation
The system handles parts of the task; the human supervises.
Higher autonomy
The system acts within a defined operating domain.
Benefits depend on the setting
Automation can improve repeatability, throughput and availability for suitable work. It can also
shift errors from isolated human mistakes to systematic software, sensor or model failures affecting
many operations. Do not assume that automation gives zero errors, unlimited uptime or a fixed
percentage improvement.
Keep the operating domain explicit
A warehouse robot may work well on a mapped, maintained floor but fail on an unfamiliar surface.
A human must understand what the system can handle, what it cannot handle and how a
handover works. Formal driving-automation levels describe a specific domain; they should not be
treated as a universal ladder for every smart appliance.

Feedback can change a policy
Describe the learning mechanism
An RL agent collects transitions: a state, an action, a reward and a next state. A learning algorithm
uses those transitions to update values or policy parameters. A positive reward does not
mechanically guarantee that an action becomes more likely in every algorithm; updates depend
on the method and its estimates of future return.
Design an illustrative delivery task
Element
Possible definition
State
Location, remaining energy and relevant obstacle information.
Action
Choose a permitted move.
Reward
Score progress and successful completion; penalise undesirable
outcomes.
Constraint
Disallow unsafe actions even if a reward would favour them.
A deployment may stop learning
A trained policy can be evaluated repeatedly on new observations without changing its
parameters. Online learning requires a controlled update process and evidence that changes
improve performance. Separate “the action changed because the observation changed” from
“the policy changed because the agent learned”.

Distinguish information from energy
A software value such as “target angle = 15 degrees” is information. Interface electronics convert
it into a suitable control signal; a powered mechanism supplies the force. Some systems use
analogue voltages, others PWM or digital commands. A DAC alone normally cannot supply motor
power. Mechanical limits, response time and feedback all affect whether an intended action is

Help people understand the system
Human-AI interaction is part of HCI
Human-computer interaction studies how people use computing systems. Human-AI interaction
focuses on challenges raised by AI, including uncertainty, adaptation, delegation and trust. It is
not a strict division between deterministic old interfaces and always-probabilistic new ones. The
important question is what the person needs to understand and control.
Useful interface information
Show
Why it helps
Current mode and operating
limits
The user knows what the system is doing.
Relevant evidence and uncertainty
The user can judge an output appropriately.
Planned action and reason
The next behaviour is less surprising.
Override, handover and recovery
The user can respond when the system cannot continue.
Avoid over-trust and under-trust
Unclear automation can cause misuse through excessive reliance, or disuse when useful assistance
is rejected. A handover should communicate the state of the task and why control is changing. A
confident-looking score is not enough: the interface should support an informed decision and an
appropriate human response.

Evaluate more than performance
Three important ethical concerns
Concern
Design question
Fairness
Who benefits, who is disadvantaged, and how was this measured?
Transparency
Can affected people understand the system’s role and limitations?
Accountability
Who is responsible for deployment, oversight and correction?
Reward design can encode priorities
A reward that values only throughput can encourage neglect of other goals. Historical data can
contain unequal representation or biased decisions. Evaluate outcomes across relevant groups
and situations rather than assuming an algorithm is neutral because it uses numbers. The
appropriate criteria depend on the task and the people affected.
Make responsibility practical
Document the intended use, data sources, limitations and monitoring process. Provide channels
to question or correct consequential outcomes. Ethical and legal requirements vary by context
and jurisdiction; no single checklist proves a system is responsible. For high-stakes uses,
performance testing and meaningful human oversight are essential parts of the deployment
decision.

Measure outcomes, not just activity

Compare meaningful outcomes such as resource use, reliability, accessibility and user experience.
